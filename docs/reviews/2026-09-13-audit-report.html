P1bugF-001

Eval 金标有一条永远匹配不上的 retrieval 关键字

证据
data/evals/sample_eval.jsonl:1 期望 "lets a model focus on the most relevant tokens"。
docs/sample/lecture5_attention.md:3 是 lets a model decide...； :10 是 lets the model focus on the most relevant tokens。 全文不存在该连续子串。harness.keyword_match_rate / reciprocal_rank 都是 needle in text（harness.py:149,179）。
现状
Q1 即使第一名命中整篇讲义，retrieval_span_hit_rate 与 RR 也最多 2/3。 两案平均上限约 0.8333。因为 span hit 永远 < 1， failure_reasons 的 elif（harness.py:235-246）让 Q1 永远发不出 retrieval_ranked_expected_span_below_first。 这不是 tasks.md 里写过的「两问打平」，是金标错误。
为何重要
测量天花板被金标锁死。任何策略、任何 rerank 都无法在 Q1 上拿到满分 RR。leaderboard 的主键被污染。
建议
1. 把关键字改成原文连续子串（例如 line 10 整句，或 line 3 的 lets a model decide）。 2. 加一条测试：每条 expected_retrieval_keywords 必须是对应 source 文件的子串。 3. 再跑 compare。
非目标
不要为此改 RR 公式或放宽成 token 集合匹配。
P1bugF-002

eval-compare 把 fallback 记成成功并送进 leaderboard

证据
Chat fallback 不抛（chat.py:89-92,156-167）。 Embedding hash fallback 不抛（embedding.py:82-90）。 agents_sdk 失败改走 basic 仍返回完整答案（agents_sdk.py:100-110）。 矩阵单元只有异常才 error/skipped（comparison.py:251-268）。 走完就是 status=ok，leaderboard 只过滤非 ok（:312-313），行内没有 provider mode。 scripts/verify_live_qdrant.py 会拒绝 fallback，但 harness/compare 不会。
现状
无 key 的 compare 仍产出完整排行榜。agents_sdk 若降级到 basic，两个 runtime 格子可以是同一条 basic 答案、不同 label。 Ask 路径 200 + UI 芯片是符合「诊断可见」的；compare 聚合层把诊断丢掉了。
为何重要
项目硬规则：不要把 fallback 当成功。这会让 Phase C 的策略对比在离线/降级时看起来「有赢家」。
建议
1. 若任一 case 的 chat/embedding/runtime 为 fallback，或 requested_runtime != actual_runtime，格子标 degraded 或直接 error，不进 leaderboard。 2. 给这条加测试（当前 test_eval_comparison.py 根本不跑 _run_matrix_case）。
非目标
不要让 Ask 在 fallback 时改成 503；Ask 的可见降级是对的。

P1bugF-004

Qdrant 源级 delete 后 upsert 失败，下一次增量 ingest 不会把点写回来

证据
qdrant_store.py:155-169：先 _delete_by_source_paths(replaced) 再 upsert，无事务。 异常发生在 ingest.py:109-132 的 save 与 manifest.save 之间则 manifest 不更新。 下次 checksum 相同 → changed_sources 为空（ingest.py:189-199）→ replaced_source_paths=[] → 不会再 upsert。 2026-08-29 审查写「直到下一次 ingest」；增量语义下「下一次」对未改动的源是空操作。
现状
该源在 Qdrant 中消失，manifest 仍声称已索引。Ask/eval 静默少一段证据。 没有测试覆盖 delete 成功、upsert 失败。ingest 单测用的 FakeQdrantStore 不是 QdrantChunkStore，isinstance(..., QdrantChunkStore) 分支从未被打到。
为何重要
这是 Phase D 生命周期的正确性漏洞，不是「以后再拆文件」的结构债。
建议
1. 失败后把该 source_path 从内存中的计划标成 dirty，或 ingest 开始时对 checksum 匹配的源做存在性抽查。 2. 最小修复也可以是：upsert 失败则不要认为 checksum 仍然有效（写一个「needs_reindex」集合进 manifest）。 3. 用假 client 测 delete-then-upsert 失败。
非目标
不要为了这个上分布式事务或换向量库。不要先拆 qdrant_store.py 当修复。

6. Agent / 检索 / Eval 专项

  • 工具面：用户能 ingest/ask/eval/compare/list；agent 只有 search/list/time。不对等是有意的交付缺口，不是 bug。不要为 action parity 把 ingest 塞进 tool。
  • 原语：tools.py 是原语。检索走完整 pipeline。SDK 却绕过 search_documents 自己 retrieve——文档真、调用图假。
  • 弱检索改写/重试：未做。Phase E。pipeline 只有 search+rerank。
  • 可观测性：只有 AnswerDiagnostics。无 tool trace / turn log。SDK 若不调用 search，citations 为空但模型仍可编 [S1]。
  • Citation 契约：[S1] 从第 0 列开始，测试锁住，未回潮。不要改成 prompt 里的检索策略。
  • basic vs agents_sdk：citation 对象模型共享；编排不同（必检索 vs 可选）。eval 能分开失败仅当 SDK 真的跑起来；fallback 到 basic 时 F-002 会把格子标成 ok。
  • 指标：RR 能量到排序；precision 能量到宽窗噪声，对重排不敏感。单元测试证明策略能排不一样；样本 eval 证明不了。

7. 前端与 API 契约

  • Ask diagnostics 在卡片上，不只 raw JSON。requested→actual、chat/embedding/rerank 芯片都在。
  • Eval 只有 raw payload。Compare leaderboard 显示 RR/precision，失败格子有 reason；成功格子没有 fallback 警告。
  • 错误：后端有 code/detail/action_hint，前端解析后只显示字符串。422 不是该形状。
  • 无路由、无历史、无上传：product-gap，未半实现。
  • 无前端测试、无 ESLint、无 error boundary。按钮有 disabled={isAsking|isActing}。
  • 无 API key 进 bundle。只暴露 VITE_API_BASE_URL。
  • 对比度可用。Ask textarea 无 label——未到有害。
